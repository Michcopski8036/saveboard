## Post 1 — SaveBoard: the admin panel that broke prod three times in 30 minutes

**Post text:**

Shipped an admin panel for SaveBoard this morning. Release config, a users tab, presence tracking. Normal Sunday feature work.

Then I deployed and broke production. Three separate times, in about half an hour.

1. New endpoint pushed the project to 13 serverless functions. Vercel's plan caps it at 12. The deploy failed — silently. No new endpoint, but production kept serving the old build like nothing happened, so I didn't even know to look. Fix: fold the new endpoint into an existing one behind a query param instead of giving it its own file.

2. Fixed that, redeployed, admin endpoints started returning FUNCTION_INVOCATION_FAILED. I'd pulled the admin-allowlist check into its own shared file and imported it from three api/ handlers. Turns out Vercel doesn't bundle api/*.ts — it transpiles each file separately. My shared import resolved fine at typecheck time and simply didn't exist at runtime.

3. Moved the shared file out of api/, redeployed — still broken, now with ERR_MODULE_NOT_FOUND. Same root cause I hadn't actually fixed: it was never about the file's location, it was that nothing bundles api/ at all. I ended up inlining the allowlist directly into all three files, with a comment telling future-me not to "clean this up" back into a shared import.

Three fixes, same underlying lesson: Vercel's API routes are per-file, not a bundle. Anything they import has to actually ship with them.

**Source:** commits `9d14880` (feature), `f51dde9` (12-function cap fix), `cb3bfc9` (first attempt at the import fix — still broken), `aeefe5e` (actual fix — inline instead of import). All four landed 09:13–09:42 on 2026-07-19.

## Post 2 — SaveBoard: a missing hook call, a white screen, and why the build had no typecheck

Last week I shipped a crash. Open the Share modal on a board, or the ⋯ menu on a shared board in the sidebar — white screen, whole app gone.

Cause: two components called `tr()` for translated strings but never called the `useLanguage()` hook that defines it. `tr` was just undefined, so React threw a ReferenceError the moment either component rendered. It was a regression from an earlier i18n pass that added `tr()` calls project-wide but missed these two.

The part that bothered me more: nothing caught it before it shipped. The repo had no tsconfig, so `vite build` never typechecked anything — it just transpiles and ships. An undefined variable name is exactly the kind of bug a typechecker catches in seconds.

Fixed the crash, then added a real tsconfig and put `tsc --noEmit` as the first step of `npm run build`, so an undefined reference now fails the build instead of reaching users. Turned up 10 pre-existing type errors once I turned it on (loose Supabase casts, a couple of react-dnd ref-callback mismatches, some COPY-object indexing) — fixed all of them to get to zero, since a gate only means something if it's actually clean.

**Source:** commit `c59c071` (the crash fix) and `52d7d14` (adding the typecheck gate + fixing the 10 errors it surfaced). Documented as the "2026-07-13 Share/Sidebar white-screen crash" in CLAUDE.md.

## Post 3 — PeriodVol: the ml numbers were wrong, off by 3-6x, and here's why

PeriodVol estimates blood loss in ml from what you log (pad size, saturation, cup fill, clots). The original per-product values were close to lab **maximum capacity** — how much a pad or tampon can hold if you fill it to the brim. That's not what you lose per change in normal use; people change products before they leak, not after.

A user measuring with a menstrual cup found the app's total came out way too high, which is what surfaced this.

Recalibrated against a different anchor: the clinical rule of thumb that a fully soaked regular pad or tampon holds about 5ml of blood. That number ties directly to the standard 80ml heavy-bleeding threshold — 16 soaked regular pads ≈ 80ml — which is the reference clinicians actually use.

The scale of the correction: a regular pad's "saturated" value went from 30ml down to 5ml. A large pad's went from 40 to 10. Tampons, liners, night pads all moved the same direction, roughly 3-6x down. Cup values didn't change — a cup reading is a direct volume measurement, so it was already the accurate one, and became the reference point everything else got tuned against.

**Source:** `docs/ml-calibration.md` (full sources: FDA tampon absorbency ranges, DeLoughery et al. 2023 BMJ Sex Reprod Health, CeMCOR clinical reference), recalibration dated 2026-06-17, also noted in CLAUDE.md. Values cross-checked against the live `PAD_ML`/tampon `levels` objects in `www/index.html` — code matches the doc.
