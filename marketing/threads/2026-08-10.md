## Post 1 — SaveBoard: 25 seconds to see your own bookmarks, and the three separate reasons why

Opened SaveBoard cold and watched the spinner for 25 seconds before a single card
showed up. Spent last Sunday tracing it, and it wasn't one bug — it was three, stacked.

**First:** every startup query — subscriptions, boards, shared_boards, storage — was
firing three times each within 5 milliseconds of each other. The data-loading effects
were keyed on the `user` object, and every auth event hands back a fresh object.
`getSession()` fires one, Supabase's `INITIAL_SESSION` event fires another, and the app
was triggering a third on itself — a `last_seen` heartbeat write that itself emits
`USER_UPDATED`. Three object references, same user, three full reloads. Fix: key the
effects on `user.id` instead of the object.

**Second:** even with duplicates gone, the load was a chain — boards, then
board_members, then links, plus a storage listing that only feeds a usage bar nobody's
looking at during startup. Each hop cost 1-14 seconds depending on how cold the
database was. Boards and board_members don't need to be sequential (the membership
rows annotate boards, they don't locate them), links doesn't need to wait on boards
either, and the storage listing had no business being on the critical path at all.
Same number of queries, one round-trip of latency instead of four.

**Third, and the one I couldn't fix:** the database itself. A token refresh took 6.2
seconds on one measured load; a 65-row query took 14 on another. That's a free-tier
Supabase instance being a free-tier Supabase instance. So instead of fighting it, I
stopped making the user wait on it — the last successful board load is now snapshotted
to `localStorage` per user and painted instantly on open, with real data swapping in
as it lands. Spinner only shows when there's genuinely nothing cached yet.

**Source:** commits `d559882` (dedupe the triple-fire), `54a75bd` (parallelize the
chain), `16c91ac` (instant paint from cached snapshot) — all three landed 2026-08-02.

## Post 2 — SaveBoard: building the dashboard that tells me what to do next, and immediately breaking it

The admin "Marketing" tab was an empty placeholder for a while — no visibility into
whether anything I was shipping actually mattered. Spent a stretch building it out
properly: weekly numbers against last week, per-path traffic with board clicks next to
it so a guide post's CTA can be judged not just admired, and a short "what needs a
decision" list generated only from data the dashboard can already show — deliberately
built so it can never point at something it has no evidence for.

The part I like best: scheduled routines (cron jobs, the same kind that write this
post) now report every run — success or failure — to a table, using only the public
anon key against an insert-only schema, so a cloud job with no secrets can still
self-report honestly. Before this, a routine that silently stopped firing looked
identical to one that ran clean. Now a missing row is the tell.

Naturally, building it broke production once: a new "traffic" block declared a second
`nowMs` in a file that already had one. Node rejects that at module load — every admin
API request started 500ing. Renamed it to `trafficNow` and moved on, but the actual
lesson was smaller and more annoying: `npm run typecheck` doesn't cover the `api/`
directory, so a duplicate-declaration error like this only ever shows up at runtime,
never at build time. Checking `api/` with `tsc` directly is now on the list.

**Source:** commits `492d510` (dashboard build-out), `6325d47` (routines self-report),
`7f23671` (DB round-trip health indicator on the System tab), `f8432a4` (activation
funnel view), `a2d4343` (the `nowMs` 500 fix) — 2026-08-02 to 2026-08-03.

## Post 3 — PeriodVol: every link on the new page reopened the whole app instead

Shipped a new `/guides` hub for PeriodVol — a page that's mostly just internal links.
Inside the native iOS and Android apps, every single one of those links did the same
wrong thing: instead of loading the page, it reopened the app from scratch.

Chased it into Capacitor's own source on both platforms. Android's
`WebViewLocalServer.handleLocalRequest` serves `index.html` whenever the last path
segment has no `.` in it and `html5mode` is on — which it defaults to, and nothing in
this project's config overrode it. iOS's `CapacitorRouter.route(for:)` does the
equivalent: an empty path extension routes to `index.html` too. Clean URLs, the thing
every other page on the site already used, are exactly what triggers this.

It had been silently true the whole time — this project just never had a page made
almost entirely of internal links before, so nothing surfaced it until the guides hub
did. Fix: append `.html` to extensionless internal links, but only when
`Capacitor.isNativePlatform()` is true, so the web's clean URLs stay canonical and
don't get redirected through an unnecessary 301. Unit-tested against the 16 real href
shapes the site actually uses. Not yet confirmed on a physical device — this only
reaches real users with the next store build, so that's still owed.

**Source:** commit `52be9e9` ("Fix internal links inside the native apps") in the
`periodvol` repo, 2026-08-06. Related, same session: `bcdefc8` records a second gotcha
found while fixing this one — a hand-patched sitemap entry that every content build was
silently deleting.
