## 1. The count that lied above 10

**Commit:** [`b94a760`](https://github.com/Michcopski8036/saveboard/commit/b94a760c7e77d9a0f9a90ce97dadb363e3038738) — "fix(admin): shared board count stuck at 10" (2026-09-19)

```
My own admin dashboard has been quietly lying to me. "N shared boards" was
the .length of an array I'd capped at 10 for a top-boards table. Which means
the count was correct — right up until the 11th shared board ever existed.
After that it's frozen at "10" forever, no matter how many more get shared.

I didn't notice because we're genuinely still under 10. The bug was sitting
there, armed, waiting for the number to matter.

Fixed it with a dedicated count query instead of reusing the capped array.
While I was in there I also left a comment explaining why that query
doesn't filter by owner — it's an admin view, so seeing every user's shared
boards together is correct, it's just that right now they're all mine and
one bot's, so it doesn't look like it.
```

**What I didn't add:** no "we now have N shared boards" number — the commit
doesn't state one and I'm not going to invent a headline stat to make the post

## 2. A bug that has zero symptoms today and one very bad day later

**Commit:** [`72e76f4`](https://github.com/Michcopski8036/saveboard/commit/72e76f4a30151fbe0897d8e9563663717887d4b7) — "fix(billing): Android restore-purchases recorded source as 'apple'" (2026-09-11)

```
Fixed a bug today that no user will ever notice — until it matters a lot.

A day earlier I'd fixed the *purchase* path to record which store a
subscription actually came from (source: 'apple' vs the real store). I
missed the *restore* path. So an Android user tapping "Restore purchases"
for a subscription they bought on Google Play would get it written to the
database as if they'd bought it on Apple.

Pro access itself was never affected — that gate only checks subscription
status, not source. What breaks is the record. And a wrong record like
this only becomes a problem the day you actually need it: a refund
dispute, reconciling revenue against what each store reports, or wiring
up the Play Developer API to verify subscriptions server-side.

The scary bugs aren't the ones that break something today. They're the
ones that quietly write down the wrong fact and wait for you to ask it a
question.
```

**What I didn't add:** no count of how many Android restores happened before
the fix — the commit doesn't say, and I'm not estimating one.

## 3. I trusted my own changelog for nine days

**Commit:** [`ee22d2b`](https://github.com/Michcopski8036/saveboard/commit/ee22d2b00f4fae1adbad3541d10b72e3c11ec7e9) — "docs: correction — Android 1.0.17 never made it to Play" (2026-09-19)

```
Small, humbling one. On Sep 10 I built Android 1.0.16, found a payment bug
same day, and rebuilt as 1.0.17. Both builds land at the exact same file
path. What actually got uploaded to Play was the file sitting there before
the second build overwrote it — 1.0.16, not 1.0.17.

My own changelog, my own task tracker, and the in-app update-gate config
all said "1.0.17 rolled out" for nine straight days. Nobody, including me,
thought to doubt it — because nothing was visibly broken. It wasn't: every
fix from 1.0.17 is cumulative in 1.0.19, which really did ship after this
was caught, on 2026-09-19.

Lesson, the boring but real kind: after an upload, read the version back
from the store console, not from the filename you built. A build number
in a build log tells you what you built, not what actually made it out
the door.
```

**What I didn't add:** no claim about user impact from the mix-up — there
wasn't any (the content was cumulative), and the post says that plainly rather
than implying otherwise for drama.
