## 1. The database was next door and the API was flying to another continent

**Commit:** [`c310c15`](https://github.com/Michcopski8036/saveboard/commit/c310c153eda697428a7a1461697f3f9ea44dbd3a) — "perf: run API functions in icn1 (Seoul, next to Supabase) + fold sequential links scan into the parallel batch"

```
The admin dashboard took ~5 seconds to load. Not because of a slow query —
because of geography.

The Supabase database lives in Seoul (ap-northeast-2). The API functions that
query it were running in US East (iad1) by default. 13 queries, each one a
trans-Pacific round trip, before the page could render anything.

Moved the functions to icn1 — same region as the database. Also found one
query that was still running sequentially after the rest, so folded it into
the parallel batch while I was in there.

Sometimes the fix isn't the query. It's where the code runs relative to the
data it's asking for.
```

**What I didn't add:** no before/after millisecond number, because the commit
message only gives the qualitative "~5s" baseline and doesn't state the measured
result after the fix — better to leave that out than estimate one.

## 2. A shared board was quietly eating a Free member's own save limit

**Commit:** [`082ce92`](https://github.com/Michcopski8036/saveboard/commit/082ce92d648a43046b90e0408d0b398d2186bce8) — "fix: shared-board links no longer consume a member's Free saves quota"

```
Found a bug where joining someone else's shared board could lock you out of
saving anything at all — on your own account, with your own 30-link Free
limit untouched.

The links list in memory merges in other people's links (the ones on a
shared board you joined, so they render alongside your own). The Free-plan
save gate was counting that whole merged list — so a 40-link board you
joined maxed out your quota before you'd saved a single link yourself.

Fixed it to count only links you actually own (user_id = you), matching
what the server already used everywhere else. Just opening a shared link
was never affected — the bug only hit once you joined a board.

The kind of bug that's invisible until you're the member on the receiving
end of someone else's popular board.
```

**What I didn't add:** the commit notes this was reproduced and verified against
"RLS-faithful fixtures (40-link board: member 0/30 was fully blocked before, saves
fine after)" — I left the specific fixture numbers out of the post since they're
test data, not a real user's experience, and stating them as if they were a live
account would misrepresent what was actually measured.

## 3. Postgres caught a one-word type mismatch before it shipped

**Commit:** [`da1da5b`](https://github.com/Michcopski8036/saveboard/commit/da1da5bacd9781ffcee61737b4520aa1ede142d1) — "fix: get_board_invite_preview return type — links.id is text, not uuid"

```
Wrote a new SQL function, ran it in the Supabase SQL editor, got error 42P13:
return type mismatch.

The function declared `id uuid` because most primary keys in this schema
are UUIDs. But links.id isn't one — it's generated client-side by a
generateId() call before the row ever reaches the database, so the column
is text.

One word, `uuid` to `text`, and it deploys clean.

This is exactly why migrations here get run against prod manually before
the client ships — a mismatch like this fails loudly in the SQL editor,
not silently in front of a user.
```
