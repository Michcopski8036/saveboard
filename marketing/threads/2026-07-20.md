Three posts, all sourced from the same stretch of Sunday-morning deploy pain

## Post 1 — the deploy that failed with no error

Vercel caps this project at 12 Serverless Functions. I found that out by going
over it.

Added a new admin endpoint, pushed, watched the deploy finish green. Except it
hadn't — the project silently stayed on the previous build. No error banner,
nothing in the deploy log I was looking at. The tell was the new endpoint
returning the SPA's index.html instead of JSON, because as far as production
was concerned, it didn't exist. 13 functions, 12-function plan, deploy just...
didn't ship.

Fix: folded the new endpoint into an existing file, routed by a `?resource=`
query param instead of a new file. One function, two jobs. Left a comment in
the code so I don't "clean it up" back into a 13th file later.

**Source:** commit `f51dde9` — "Fix failed deploy: fold app-config into
admin-stats to stay under 12 functions"

## Post 2 — fixed it, redeployed, still broken

Every admin API route started returning `FUNCTION_INVOCATION_FAILED` in
production. Typechecked clean locally. Ran fine in dev.

First theory: the shared file they all imported was named `api/_admins.ts`,
and Vercel silently excludes underscore-prefixed files from the `api/`
build. Moved it to `src/shared/admins.ts`, redeployed, confident.

Still broken — now `ERR_MODULE_NOT_FOUND` in the runtime logs. Turns out the
underscore was never the problem. Vercel doesn't bundle `api/*.ts` files, it
transpiles each one individually. A relative import to a shared module
resolves fine at typecheck time and is simply absent from the deployed
function. My first fix looked right and wasn't.

What actually worked: stop importing it. Inlined the allowlist and the token
check directly into each of the three admin endpoints. Uglier, duplicated,
and it's the version that's actually present when the function runs.

**Source:** commits `cb3bfc9` ("move shared admin module out of api/") and
`aeefe5e` ("inline the allowlist instead of importing it") — same Sunday
morning, second commit is the real fix.

## Post 3 — the crash and the check that would've caught it

An i18n commit added `tr()` calls inside a couple of components — the board
share modal, a sidebar dropdown item — that never called `useLanguage()` in
their own scope. `tr` was `undefined`. The moment someone opened the Share
modal or a board's `⋯` menu, React threw and the whole app went white.

This repo had no `tsconfig.json`, so Vite/esbuild never typechecked anything
— an undefined name just shipped straight to prod.

Fix for the crash was two lines (`const { tr } = useLanguage();` in each
component). Fix for the class of bug was bigger: added a tsconfig and made
`tsc --noEmit` the first step of `npm run build`, so any undefined reference
now fails the build before it fails a user's screen.

**Source:** commit `c59c071` — "fix(i18n): white-screen crash — tr() called
without useLanguage() in child components"; systemic fix in `52d7d14` —
"build: add tsconfig + tsc typecheck gate to catch undefined-reference
crashes"
